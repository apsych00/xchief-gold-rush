Today the client decides when a task is done and calls `claim_task`; that is the fraud surface this ticket closes. After it, every reward is released by the server from state it tracked itself.

Decisions (do not redesign):
1. `public.tasks` gains `kind text not null default 'manual'` (`video`, `redirect`, `email`, `signup`, `instagram`, `manual`) and `url text`; the seed sets kind per row (video -> `video`; instagram -> `instagram` (B8); telegram, youtube, story, review_* -> `redirect` with their URLs moved from src/config.js into the seed; email -> `email`; signup -> `signup`). `get_tasks()` returns `kind` and `url`; the client renders from the server list and keeps no task table of its own (delete the client-side TASKS constant path in src/useGame.js once nothing reads it).
2. Video (B6): table `public.video_progress(player_id, task_id, seconds_watched int, duration int, started_at, updated_at, primary key (player_id, task_id))`. Client sends `{type:'task_progress', task:'video', seconds, duration}` at most every 5 s while the video plays and once on ended; the server upserts and, when `seconds_watched >= 0.9 * duration` and duration >= 10, calls `claim_task` itself and answers the usual `me` with `reward`. A `claim_task('video')` from the client is refused with `not_claimable`. Progress cannot go backwards and cannot exceed `duration + 5`; the server rejects a `seconds` jump larger than 2x the wall-clock time since the last report (`progress_too_fast`), so a client cannot fast-forward.
3. Redirect and return (B7): client sends `{type:'task_start', task}` before opening the URL; the server records `task_visits(player_id, task_id, started_at, returned_at)` and answers `{type:'task_started', task, window_ms: 5000}`. When the tab regains focus the client sends `{type:'task_return', task}`; the server releases the reward only if `now() - started_at >= 5 s` and no reward exists for that task on this device or verified email (B5's rule), else `not_yet` (with `retry_ms`) or `already_claimed`. Lenient by design (B13 hardens): one visit per task per device is enough.
4. Email verified (B9): `verify_otp_code` success releases the `email` task itself (server-side, same `me` + `reward` shape) and, if the player has just become verified for the first time on this device, the `signup` task. Remove the client's `onClaim('email')` and `onClaim('signup')` effects in src/Tasks.jsx and the Trader-level CTA path that calls `claim_task('signup')` for unverified players (G1): that CTA now opens the OTP screen.
5. All new frames go through `handleFrame` with the same error shape; kiosks get `not_available`. `claim_task` from the client remains only for `kind='manual'` (none seeded; keep for future use).
