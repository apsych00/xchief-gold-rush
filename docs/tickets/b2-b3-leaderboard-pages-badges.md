Decisions (do not redesign):
1. `public.leaderboard(p_tournament text default null, p_page int default 1)` returns 20 rows per page ordered by record desc, then updated_at asc (earlier record wins ties), with `rank`, `display`, `record`, `tier`. Page 1 is what the socket pushes live. `public.my_rank(p_tournament text default null)` returns the caller's own `{rank, display, record, tier, total}` or null when the caller has no verified email or no score in that tournament. Own-row identity is the player id, never the masked string (closes G3).
2. Frame shapes. Request `{type:'leaderboard', tournament?, page?}` answers `{type:'leaderboard', tournament, tournaments, page, pages, total, rows:[{rank, display, record, tier}], me:{rank, display, record, tier} | null}`. The live push after a settle carries page 1 plus `me` computed for each receiving socket (one SQL call per socket is acceptable at 100 concurrent; keep the existing 1 s throttle). `me.rank` is the row the client highlights and pins as the sticky bottom row when it is off the visible page.
3. Badge tiers (B3), stored with the rank, not the player: table `public.badge_tiers(tier text primary key, title text not null, min_rank int not null, max_rank int, icon text not null, sort int not null)`; seed: `gold` 1-1 "/badges/gold.svg", `silver` 2-2, `bronze` 3-3, `top10` 4-10, `top100` 11-100, `player` 101-null. `tier` on every leaderboard row and on `me` is the tier whose range contains the rank. `public.badge_legend()` returns the table ordered by sort; the `leaderboard` frame carries `legend` once (on request, not on push). Six placeholder SVGs under `public/badges/` using only existing colour tokens.
